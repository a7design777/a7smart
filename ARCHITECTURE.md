# Архітектура a7smart

Документ для того, хто продовжуватиме роботу. Описує не лише «що де лежить»,
а й **чому саме так** — більшість рішень ухвалені під конкретні обмеження,
і без них виглядають довільними.

---

## 1. Обмеження, з яких усе випливає

| Обмеження | Наслідок |
|---|---|
| **Жодного заліза вдома** (вимога користувача, не тимчасова) | Усе тільки через хмарні API виробників. Локальні протоколи, шлюзи, Zigbee-стіки виключені |
| **Сервер 1 vCPU / 1 GB RAM**, спільний з Traefik, n8n, flowise, a7cms | mem_limit 256m, збірка образу в CI, важкі залежності заборонені. Home Assistant відкинуто саме тому — потребує 2 GB |
| **Квота Tuya API скінченна** | Стани читаються з кешу сервера, а не з хмари на кожен запит. Будь-яка фіча, що ходить у Tuya на кожен рендер, — помилка |

Користувачі — власник і сім'я. **Мультитенантності, ролей і реєстрації немає
за задумом.** Один спільний пароль, одна сесійна cookie.

## 2. Топологія

```
Браузер ──HTTPS──> Cloudflare ──> Traefik (мережа n8n-docker_default)
                                     │
                                     ▼
                            контейнер a7smart :3000
                            ├── Hono API  (/api/*)
                            └── статика React (усе інше)
                                     │
                     ┌───────────────┼────────────────┐
                     ▼               ▼                ▼
              Tuya Cloud      Remihome portal      Neon Postgres
             (openapi.        (proxy.              (історія,
              tuyaeu.com)      remihome.es)         каталог, сценарії)
```

Один контейнер віддає і API, і фронтенд — щоб на Traefik був один роутер,
а в пам'яті один процес. Портів назовні не публікується.

## 3. Потік даних

### Читання — фоновий поллер, server/src/poller.ts

```
раз на POLL_INTERVAL_MS (5 хв)
  │
  ├─ кожен 12-й цикл: перечитати каталоги обох провайдерів → upsert у devices
  │
  ├─ Tuya:     getDevicesStatus(ids)  → normalize()         → stateCache
  ├─ Remihome: /devices/all/status    → normalizeRemihome() → stateCache
  │
  └─ метрики з HISTORICAL_KEYS → таблиця readings
```

stateCache — це Map у пам'яті процесу. **Дашборд читає виключно з нього.**
Перезапуск контейнера означає порожній дашборд до першого циклу.

### Запис — керування

```
POST /api/devices/:id/command
  │
  ├─ getProvider(id) → 'tuya' | 'remihome'
  ├─ Tuya:     POST /v1.0/iot-03/devices/{id}/commands  [{code, value}]
  ├─ Remihome: PUT  /devices/{code}/status              [{name, value}]
  │
  ├─ пауза 900 мс (щоб прилад устиг застосувати)
  ├─ refreshDevice(id) — перечитати ЦЕЙ пристрій і оновити кеш
  └─ відповідь містить свіжий state
```

**Крок refreshDevice критичний.** Без нього дашборд читав би старий кеш і
показував, що команда «відкотилася» — навіть коли вона успішна. Це була одна
з двох причин, чому спершу не працював фанкойл.

## 4. Провайдери

### Tuya — основний, читання й керування

Клієнт server/src/tuya/client.ts **не використовує офіційний SDK**:
@tuya/tuya-connector-nodejs не оновлювався з квітня 2022 і тягне axios ^0.21
з відомими CVE. Підпис реалізований власноруч:

```
stringToSign = METHOD \n SHA256(body) \n <signature-headers> \n <path?sorted-query>
str (токен)  = client_id + t + nonce + stringToSign
str (решта)  = client_id + access_token + t + nonce + stringToSign
sign         = HMAC-SHA256(str, secret).toUpperCase()
```

Залежностей нуль.

**Читання статусів має три стратегії** (tuya/devices.ts), які пробуються
по порядку вартості на кожній пачці:

1. GET /v1.0/devices/status — повертає **об'єкт** {id: status[]}
2. GET /v1.0/iot-03/devices/status — повертає **масив** {id, status}
3. поштучно GET /v1.0/devices/{id}/status

Стратегія навмисно **не закріплюється**: одна невдала пачка інакше перевела б
систему назавжди на поштучне читання (46 викликів замість 3). Чинна стратегія
видна в /api/health.

**Проблемні пристрої.** Якщо Tuya відмовляє в статусі одного пристрою, вона
відхиляє **весь гуртовий запит** із 1106 permission deny, а не пропускає його.
Такі пристрої запам'ятовуються в наборі problematic і виносяться з пачок;
якщо пристрій оживає — повертається автоматично.

### Remihome (Remica) — необов'язковий

Публічного API немає. Використовується той самий інтерфейс, що й веб-портал
proxy.remihome.es: логін формою → сесійна cookie → JSON.

```
POST /proxy/login                        username, password (form-urlencoded)
GET  /{installation}/RemicaHome/devices?includeHidden=false
GET  /{installation}/RemicaHome/devices/all/status?includeHidden=false
GET  /{installation}/RemicaHome/zones
PUT  /{installation}/RemicaHome/devices/{code}/status   [{name, value}]
```

Формат керування отриманий **читанням JS-бандла порталу**, а не підбором:
main.b9cf3614.js містить функцію, яка робить PUT на devices/{code}/status
з тілом [{name, value}], беручи значення з переліку states самого пристрою.

Важливі відмінності від Tuya:

- значення **завжди рядки** і в **реальних одиницях** ("24.67" = 24.67 °C).
  Масштабування, як у Tuya, тут не потрібне
- пристрій **самоописовий**: type.properties містить format, interaction
  (display/exec) і перелік states. Тому нормалізація будується з метаданих,
  а не з ручного списку кодів
- провайдер вимикається відсутністю REMIHOME_* у конфізі, і його відмова
  **ніколи не валить Tuya** — стан видно окремо в /api/health

Керування обмежене явним списком mode/speed/state/setpoint: метадані позначають
exec також для running_state та interruption_cause, але це діагностика, і
робити з них кнопки на системі опалення не можна.

**Ризик:** інтерфейс недокументований і може зламатися при оновленні порталу.
Це свідомо прийнято.

## 5. Нормалізація — доменна модель

Обидва провайдери зводяться до однієї структури (tuya/normalize.ts):

```ts
interface NormalizedDevice {
  id, name, kind, online
  gangs:   Gang[]           // вимикачі; onValue/offValue — бо вендори різні
  target:  {code, value, min, max} | null   // цільова температура
  metrics: Metric[]         // числові показники
  states:  StateFlag[]      // стани-переліки; alarm=true для протікання/газу
  options: OptionControl[]  // перемикачі варіантів (швидкість, режим)
}
```

Gang.onValue / offValue існують саме тому, що **Tuya приймає булеве true/false,
а Remihome — рядки "on"/"off"**. Раніше це було одне булеве поле, і в Remihome
летіло "true" — прилад мовчки ігнорував команду.

**Де правити, коли на дашборді бракує показника:**

- Tuya → server/src/tuya/normalize.ts (мапи METRICS, STATES, GANG_LABELS)
- Remihome → server/src/remihome/normalize.ts (переважно підхопиться саме)

Коди Tuya **вгадувати не можна** — вони різні для кожної моделі.
Запускати npm run tuya:probe.

## 6. Схема даних (Neon Postgres)

```
apartments     id, slug, name, sort_order, is_main
devices        external_id PK, provider, apartment_id, name, category, kind,
               enabled, sort_order, source_zone, synced_at
readings       device_id, key, value, ts          ← часовий ряд
scenes         id, name, apartment_id, icon, sort_order
scene_actions  scene_id, device_id, code, value, value_type, position
```

Нюанси:

- external_id — ідентифікатор **будь-якого** провайдера (раніше звався tuya_id)
- is_main має **частковий унікальний індекс** WHERE is_main — головна лише одна
- **sort_order у devices спільний на всі квартири.** Тому перестановка в UI
  зберігає **повний** порядок, інакше сортування в інших квартирах ламається
- scene_actions.value_type потрібен, щоб відновити форму значення при виконанні
- видалення квартири не видаляє пристрої (ON DELETE SET NULL)

Міграції — прості SQL-файли, застосовуються **з локальної машини**
(npm run db:migrate), а не з контейнера: Neon спільний, сервер не навантажуємо.

## 7. Фронтенд

React 19 + Vite + Zustand. Стан оновлюється поллінгом раз на 15 с — це дешево,
бо сервер віддає з кешу.

**Код-спліт обов'язковий:** recharts і hls.js разом важать ~800 kB.
Початковий бандл ~69 kB gzip; графіки, камери та сценарії вантажаться на вимогу.
Дашборд відкривають переважно з телефона.

**Перетягування скрізь на Pointer Events**, ніде не HTML5 DnD — останній не
працює на тач-екранах:

- useDragAssign.ts — пристрої по квартирах
- useDragSort.ts — порядок віджетів

Ціль визначається через document.elementFromPoint, бо під час setPointerCapture
сусідні елементи власних подій не отримують.

**Режим редагування** (кнопка ⠿) навмисно **вимикає керування**: змішувати
перетягування з вимикачами на телефоні означає регулярно вмикати щось замість
перетягування. Перетягування починається лише з ручки — інакше не можна було б
поставити курсор у поле назви.

**Теми:** дві, через [data-theme] на <html>. Світла побудована на палітрі
референсу Zyniq: #E8E8F7 фон, #213CCC акцент, #444D67 приглушений текст.
Без атрибута діє системна вподоба.

**Тач-цілі ≥44px.** Перемикачі візуально 50×29, але мають розширену зону
натискання через ::before з від'ємними відступами.

## 8. Сценарії

Іменований набір дій, що виконується однією кнопкою (server/src/scenes.ts).

Дії виконуються **послідовно**, а не паралельно: команди пачкою впираються в
обмеження частоти хмари, а порядок часто має сенс (спершу увімкнути прилад,
потім задати режим). Відмова однієї дії **не скасовує решту** — відповідь
перелічує, що саме не пройшло.

**Розкладів і тригерів немає** — це ручні сценарії. Автоматизація за часом чи
подією потребує окремого планувальника; змішувати її в ту саму таблицю означало б
закласти складність наперед.

## 9. Діагностика

```bash
npm run status          # стан бази: пристрої за джерелом і типом, обсяг історії
npm run tuya:probe      # сирі DP-коди Tuya + перевірка HLS камер
npm run remihome:probe  # структура відповідей Remihome, дамп у .artifacts/
```

/api/health — головна точка входу при будь-якій поломці:

```json
{
  "version": "<git sha>",
  "ok": true,
  "lastPollAt": "...",
  "lastError": null,
  "tuyaAuthProblem": false,
  "statusStrategy": "bulk-v1",
  "remihome": {"enabled": true, "lastError": null}
}
```

- version — ЩО САМЕ розгорнуто; звіряти першим ділом
- tuyaAuthProblem: true — майже завжди прострочений IoT Core
- statusStrategy: per-device — підвищена витрата квоти

## 10. Пастки, на яких уже спіткнулися

1. **docker pull мовчки віддає старий образ**, якщо збірка в CI ще триває.
   Тричі виглядало як «оновив, змін немає». Тому в /api/health є version —
   звіряти ПЕРШИМ ділом, до будь-якої іншої діагностики.
2. **Термін дії Tuya IoT Core.** Безкоштовний, але скінченний, продовжується
   вручну через Cloud → My Services. Коли спливе — код 1010/1106 і мертвий
   дашборд без видимої причини.
3. **Один зламаний пристрій валить весь гуртовий запит Tuya** (1106). Див. §4.
   Зараз такий є: «White big switch» (80174007c4dd572638b9).
4. **Камери потребують окремої підписки** на відео-API в Tuya: Service API →
   Go to Authorize → сервіс зі словом Video/Live Stream. Без неї — 28841101.
5. **Автозапуск відео.** Атрибут autoplay спрацьовує при початковому
   завантаженні джерела, а hls.js підключає потік пізніше — тому відтворення
   запускається явно на MANIFEST_PARSED, з кнопкою як запасним варіантом.
6. **Кеш станів після команди.** Див. §3.
7. **GHCR не приймає fine-grained токени** — тільки classic із read:packages.
   Помилка denied: denied виглядає як невірний пароль.
8. **Затримка керування 0.5–2 с** — наслідок хмарного шляху, не баг. Тому в UI
   оптимістичні оновлення та дебаунс на стрілках температури.

## 11. Що можна робити далі

Не зроблено свідомо, у порядку ймовірної корисності:

- **Автоматизації** — розклад і тригери для сценаріїв. Потребує планувальника
  на сервері; найпростіше — setInterval з перевіркою умов, бо cron-подібна
  точність тут не критична
- **Керування термостатами Remihome через setpoint.** Читання й запис
  реалізовані, але на живих приладах не перевірялися — під час розробки всі
  три термостати були offline
- **Real-time від Tuya** через Pulsar замість поллінгу — прибрало б затримку
  до 5 хв у відображенні станів, але потребує окремої підписки
- **Розділити sort_order по квартирах** — зараз спільний, і це вже створює
  неочевидну поведінку при перетягуванні
- **Розібратися з «White big switch»** — він у каталозі, але не віддає статус;
  найпростіше перепривʼязати його в Smart Life
